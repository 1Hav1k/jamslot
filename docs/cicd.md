# CI/CD для системы бронирования репетиционных баз «JamSlot»

Документ описывает настройку непрерывной интеграции и доставки (CI/CD) для микросервисной
системы, реализованной в лабораторной работе №4.

## 1. Выбор платформы CI/CD

Для проекта выбрана **GitHub Actions**. Обоснование:

- **Репозиторий уже размещён на GitHub** — не требуется разворачивать отдельный
  CI-сервер (Jenkins/TeamCity) и настраивать вебхуки.
- **Матричные сборки** (`strategy.matrix`) позволяют одним workflow параллельно
  проверить сразу все сервисы, не дублируя конфигурацию.
- **Встроенное хранилище секретов** (`GITHUB_TOKEN`, `secrets.*`) — закрывает
  требование «секреты не хранятся в коде».
- **Интеграция с Pull Request** — статус проверок отображается прямо в PR,
  что удобно для code review.
- **Бесплатный тариф** для публичных репозиториев и щедрый лимит минут для приватных.
- **GitHub Container Registry (GHCR)** доступен «из коробки» через `GITHUB_TOKEN`,
  что упрощает CD-этап публикации образов.

## 2. Архитектура пайплайна

Пайплайн описан в файле `.github/workflows/ci-cd.yml` и состоит из трёх джобов,
выполняемых последовательно:

```
┌─────────────┐     ┌──────────────────┐     ┌──────────────────┐
│    test     │ ──▶ │   build-image    │ ──▶ │     publish      │
│ (матрица:   │     │ (матрица:        │     │ (только main,    │
│  все 6      │     │  все 6 сервисов) │     │  booking-service)│
│  сервисов)  │     │                  │     │                  │
└─────────────┘     └──────────────────┘     └──────────────────┘
```

| Джоб | Что делает | Условие запуска |
|------|------------|-----------------|
| `test` | Устанавливает зависимости, запускает unit- и integration-тесты для каждого сервиса | push в `main`/`master`/`lab5`, PR в `main`/`master` |
| `build-image` | Собирает Docker-образ каждого сервиса из общего `Dockerfile` | после успешного `test` |
| `publish` | Публикует образ `booking-service` в GHCR с тегами `latest` и `<sha>` | только push в `main`/`master` |

### 2.1. Матрица сервисов

В матрицу включены все компоненты системы:

- `venue-service` — управление площадками;
- `booking-service` — бронирования;
- `payment-service` — платежи;
- `equipment-service` — инструменты и оборудование;
- `notification-service` — уведомления;
- `api-gateway` — точка входа.

Это покрывает минимальное требование ЛР (не менее 3 сервисов) с запасом.

### 2.2. Триггеры

```yaml
on:
  push:
    branches: [ main, master, lab5 ]
  pull_request:
    branches: [ main, master ]
```

Ветка `lab5` используется как рабочая при разработке ЛР5. После merge PR в `main`
её можно убрать из триггеров, чтобы не гонять лишние сборки.

### 2.3. CD-этап и защита основной ветки

Публикация образа ограничена условием:

```yaml
if: github.ref == 'refs/heads/main' || github.ref == 'refs/heads/master'
```

Это гарантирует, что:

- на PR и в рабочей ветке `lab5` выполняется только CI (test + build);
- образ попадает в реестр **только после merge в основную ветку**.

В этапе `publish` используется только `booking-service` — этого достаточно
по требованиям ЛР («CD хотя бы для одного сервиса»). При желании матрицу `publish`
можно расширить.

## 3. Безопасность и секреты

- Публикация в GHCR выполняется через автоматический `GITHUB_TOKEN`, который
  GitHub Actions выдаёт на время выполнения джоба. Дополнительные секреты
  не требуются и в репозитории не хранятся.
- В джобе `publish` явно выставлены права:
  ```yaml
  permissions:
    contents: read
    packages: write
  ```
  Это минимально необходимый набор для загрузки образа.
- Никакие ключи, пароли и токены не хранятся в коде и не коммитятся.
  При необходимости добавить сторонние секреты (например, Docker Hub) они
  задаются в **Settings → Secrets and variables → Actions**.

## 4. Кэширование и скорость

Для ускорения повторных сборок используются:

- **Кэш pip** (`actions/cache@v4` по ключу `hashFiles('**/requirements*.txt')`) —
  зависимости переустанавливаются только при изменении файлов требований.
- **Кэш Docker-слоёв** (`cache-from: type=gha`, `cache-to: type=gha,mode=max`) —
  повторная сборка образов использует слои из предыдущих прогонов.

Дополнительно используется `fail-fast: false` в матрице: падение одного сервиса
не отменяет проверку остальных, что удобно для диагностики.

## 5. Как проверить работу пайплайна

### 5.1. Локально (без GitHub Actions)

```bash
# 1. Установить зависимости
pip install -r requirements-dev.txt

# 2. Запустить unit-тесты
pytest tests/unit -v

# 3. Запустить integration-тесты
pytest tests/integration -v

# 4. Собрать Docker-образ одного сервиса вручную
docker build --build-arg SERVICE_NAME=booking-service -t booking-service:local .
```

### 5.2. На GitHub

1. Открыть вкладку **Actions** в репозитории:
   `https://github.com/1Hav1k/jamslot/actions`.
2. Выбрать workflow **CI/CD Pipeline** и последний запуск.
3. Убедиться, что джобы `test` и `build-image` завершились зелёным.
4. Для прогона на `main` проверить, что `publish` выполнился успешно.
5. Перейти в раздел **Packages** профиля и убедиться, что появился пакет
   `booking-service` с тегами `latest` и `<sha>`.

## 7. Автоматический деплой в staging (self-hosted runner)

Для демонстрации полного CD-цикла настроен автоматический деплой в тестовое
окружение на локальной машине разработчика (MacBook Air M1, ARM64) с
использованием **self-hosted GitHub Actions runner**.

### 7.1. Архитектура деплоя

```
GitHub Actions (облако)
        │  (раннер забирает задание по исходящему HTTPS)
        ▼
┌─────────────────────────────────┐
│  MacBook Air M1 (ARM64)         │
│  ├── GitHub Actions Runner      │
│  │   (labels: self-hosted,      │
│  │    macOS, ARM64)             │
│  ├── Docker Desktop             │
│  └── Workspace раннера          │
│       └── docker-compose.staging.yml │
└─────────────────────────────────┘
```

Джоб `deploy-staging`:
1. Запускается на self-hosted раннере с метками `self-hosted`, `macOS`, `ARM64`.
2. Разворачивает код через `actions/checkout@v4` в рабочем каталоге раннера.
3. Проверяет доступность Docker и архитектуру (`arm64`).
4. Пересобирает и перезапускает контейнеры нативно под ARM64:
   `docker compose -f docker-compose.staging.yml up -d --build`.
5. Выполняет health-check (вывод статуса контейнеров).

### 7.2. Установка self-hosted runner

1. **Settings → Actions → Runners → New self-hosted runner**, выбрать macOS / ARM64.
2. Выполнить команды из UI: скачать архив, распаковать, `./config.sh --url ... --token ...`.
   При конфигурации указать метки `self-hosted,macOS,ARM64` (метки по умолчанию
   уже включают `self-hosted` и `macOS`, дополнительно добавлена `ARM64`).
3. Установить как сервис:
   ```bash
   ./svc.sh install
   ./svc.sh start
   ./svc.sh status
   ```
4. Убедиться, что в **Settings → Actions → Runners** раннер отображается как **Idle**.

### 7.3. Требования к машине

- **Docker Desktop for Apple Silicon** установлен и запущен.
- Включён автозапуск Docker Desktop при входе в систему.
- Mac не уходит в сон при подключённом питании
  (**System Settings → Battery → Options → Prevent automatic sleeping on power adapter**).

### 7.4. Секреты

Джоб `deploy-staging` **не требует секретов**: SSH-подключение не используется,
всё выполняется локально. `GITHUB_TOKEN` автоматически доступен для `actions/checkout`.

### 7.5. Особенности ARM64

- VM отсутствует; деплой идёт прямо на Mac.
- Образы в `build-image` и `publish` собираются в облаке с `platforms: linux/arm64` —
  это гарантирует совместимость с ARM64 Mac.
- В `deploy-staging` образы пересобираются **нативно** на Mac (без эмуляции),
  поэтому сборка быстрая и предсказуемая.

### 7.6. Ручной запуск

Деплой можно запустить вручную из вкладки **Actions → CI/CD Pipeline → Run workflow**
(триггер `workflow_dispatch`). Удобно для демонстрации без лишних коммитов.

### 7.7. Безопасность self-hosted runner

- Раннер зарегистрирован только для этого репозитория (не для организации).
- Деплой выполняется только при push в `lab5` или вручную. PR из форков
  деплой не запускают, так как `github.ref` для них — `refs/pull/.../merge`.
- Не рекомендуется использовать self-hosted раннер на публичных репозиториях
  с недоверенными контрибьюторами. Для учебного проекта это допустимо.

### 7.9. Порты staging

Staging использует сдвинутые host-порты, чтобы работать одновременно с локальным
окружением:

| Сервис | Локально | Staging |
|--------|----------|---------|
| API Gateway | 8000 | **9000** |
| PostgreSQL | 5433 | **5434** |
| RabbitMQ UI | 15672 | **15673** |
| WireMock | 8089 | **8090** |
| Mailpit | 8025 | **8026** |

Проверка после деплоя: `curl -sf http://localhost:9000/health`.
